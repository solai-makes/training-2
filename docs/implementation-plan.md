# training2 フルロードマップ・実行計画

作成日: 2026-10-07

README.mdとユーザー作成のロードマップを基準にした計画。
各Step0〜14は成果物と検証結果を確認して完了とする。

## 1. ゴールと対象範囲

Dev Container内でTypeScriptモノレポのMini EC Siteを構築し、次を学習・実践する。

- REST APIとOpenAPIによるContract First開発。
- PostgreSQLを正としたDB定義とPrismaによる型生成。
- Screen Contractによる画面仕様・ルート・E2Eの整合性管理。
- 商品登録・一覧・検索、注文作成・確定・キャンセル、在庫表示。
- トランザクションと排他制御による在庫の整合性維持。
- CI/CD、コンテナ運用、AI AgentによるStep単位の開発。

GraphQLは対象外。決済・配送・商品編集や削除などREADMEにない機能は、初期案では対象外とする。

## 3. 共通ルール

### 開発とPR

- 実装、依存関係の導入、生成、テストはDev Container内で行う。環境構築に必要な設定の準備はその起動前に行う。
- Step1完了後、ユーザーがGitHubリポジトリを作成し初回pushする。既存リポジトリがある場合はその状態を確認して利用する。
- Step2以降は `step/NN-xxx` のブランチで作業し、検証後にPRを作成する。
- 原則、前Stepの変更が統合された既定ブランチから次Stepを開始する。PR作成を自動マージの許可として扱わない。
- PRには変更内容、完了条件、検証結果、残る課題を記載する。
- 課題は `ISSUES.md` に、該当Step・影響・解決条件とともに記録する。
- 使用するツール・依存関係・コンテナイメージのバージョンは各Stepで選定して固定する。

### 設定と秘密情報

- AGENTS.mdに従い、`.env`を参照・変更・コミットしない。
- 開発用設定はComposeなどで明示する。`.env`に依存する暗黙の読み込みも避ける。
- `packages/config`はプロセスに渡された環境変数をZodで検証する役割とし、`.env`を読み込む役割を持たせない。
- 秘密情報はGitHub Actionsや配備先のSecret管理に置き、ログへ出力しない。
- 配備先や本番変更の扱いはStep14で定義する。AGENTS.mdにない追加ルールを既存ルールとして記載しない。

### SSOTと生成物

| 契約 | 定義の正 | 生成・利用先 |
| --- | --- | --- |
| Database Contract | `packages/postgres/migrations`のSQL | PostgreSQL → Prisma Schema → Prisma Client |
| API Contract | `packages/api-contracts`のRoute Definition・Zodスキーマ | OpenAPI、APIルートへの組み込み、API Client |
| Screen Contract | `packages/screen-contracts` | 画面Docs、ルート検証、E2E対応検証 |

- Prisma SchemaとClientは生成物として扱い、手編集しない。Prisma migrationでDB定義を管理しない。
- PostgreSQL配下の補助SQLとmigrationsの関係を定義し、同じ定義の二重管理を避ける。
- APIの業務ハンドラーは手実装する。契約の生成で業務処理まで生成できる前提にしない。
- `packages/api-routes`は初期構成に追加せず、APIアプリが`api-contracts`を利用する。追加が必要になった場合は責務と理由を設計判断として記録する。
- 生成物ごとに、Gitへ保存するか、ビルド時に生成するかを決める。
- 保存する生成物は再生成して差分を確認する。保存しない生成物はクリーン環境での生成とビルドを確認する。

### 確定したSSOTの設計方針

- DBスキーマの変更は必ずGit管理されたSQL migrationsを起点とし、DBへ直接DDLを実行して設計を変更しない。
- 最新スキーマ一覧はmigrationsの適用結果から生成する。migrationsと最新定義を別々に手編集しない。
- Prismaの生成・CI検証は空の一時PostgreSQLにSQL migrationsを適用して行い、開発DBだけに存在する変更に依存しない。
- Prismaで表現できないDB制約は、実PostgreSQLの結合テストで動作を検証する。制約自体のテストではAPI検証を経由せず、DBへ不正値を書き込んで拒否を確認する。
- DBモデルとAPI DTOは分離し、公開項目と金額・日時などの表現を明示的に変換する。初期実装では小さな変換関数を用い、大規模なMapper基盤は導入しない。
- API契約のZodスキーマはOpenAPIへ生成可能な形式に限定する。在庫・注文状態など実データに依存する業務検証はサービス層で行う。
- バックエンドは契約を利用したルート・リクエスト検証と、auth・loggerなどのミドルウェアを組み合わせる。
- public/private APIアプリ側で、送信前のレスポンスを契約スキーマで実行時検証する。共通処理にして適用漏れを防ぎ、型チェックのみで代替しない。
- 不正なレスポンスはサーバー側の不具合として扱い、内部情報や不正な応答を送信せず、契約に沿ったサーバーエラーと秘匿化したログで扱う。エラー応答の生成・検証が再帰しない構成にする。
- 契約との整合性テストに加え、業務要件から定義した受け入れ・競合テストを維持する。契約からの自動生成テストだけで業務の正しさを判定しない。
- 破壊的変更はCIで検出し、互換性への影響・変更理由・移行方法をPRでレビューする。DB・API・フロントの配備順序と旧版が共存する期間の扱いを定める。

フロントのフォーム検証・スキーマ共有方式と追加ツールの採用は未決定。次の選択肢をStep5・9で評価し、確定した方針と区別して記録する。

- フロント向けに入力スキーマを直接公開する方式、またはOpenAPIからClientと検証スキーマを生成する方式。
- フォーム固有の入力変換とAPI入力検証の接続。送信時に検証済みなら同じ検証を重ねない。バックエンドでの検証は必須とする。
- Orval、SQL migration管理ツール、Spectral、oasdiffなどの採否。ツール名は候補であり採用済みではない。`.env`の暗黙読み込みを含め、プロジェクトの制約に適合する設定を確認する。

## 5. Step詳細

### Step0: 業務仕様と受け入れ条件

**目的:** DB・API・画面の前提を揃える。

実施内容:

- 商品コードの一意性、価格の通貨・精度、数量・在庫の入力制約を決める。
- 商品検索の完全一致・部分一致、条件併用、並び順、ページングを決める。
- 注文状態と遷移を定義する。初期案は`draft → confirmed → cancelled`と`draft → cancelled`。
- 注文作成時には在庫を減らさず、確定時に減らす。確定済み注文のキャンセルでだけ在庫を戻す。
- 複数商品の注文、同一商品の重複、価格の保存時点と合計金額の算出を決める。
- 注文作成・確定・キャンセルの再送時の扱いをそれぞれ決める。二重引当・二重復元を禁止する。
- 管理者・購入者の権限、注文所有者の識別方法、各操作の認証要否を決める。public APIが認証不要とは限らない。
- 状態競合、在庫不足、入力不正、未認証、権限不足などの応答を決める。
- 対象外機能と初期リリースの範囲を決める。

成果物:

- `docs/requirements.md`
- `docs/architecture.md`
- `docs/acceptance-scenarios.md`（シナリオID付き）

完了条件:

- 全業務操作の入力・正常結果・異常結果・権限を説明できる。
- 注文状態ごとの在庫増減と、再送・競合時に守る条件が明記されている。
- DB/API設計に影響する未決定事項が解消されている。

### Step1: Dev Containerとモノレポ基盤

実施内容:

- 既存設定の参照先を補い、開発コンテナ・PostgreSQL・cognito-localを起動する。
- 既存のサービス名`app`、ワークスペースパス、Compose参照を整合させる。サービス名を変更する場合は関連設定も合わせる。
- pnpm workspace、TypeScript、Biome、4アプリと共有パッケージの骨格を作る。各パッケージのtypecheck・test・buildはpnpmの再帰実行でまとめて実行する。
- `.gitignore`、ロックファイル、ツールの固定バージョン、共通コマンドを整える。
- API用3000/3001、フロント用5173/5174、認証用9229などのポートと接続先を整理する。
- ブラウザからのURLとコンテナ内からのURL、issuer、JWKSの関係を整理する。
- 小さな接続検証で、ローカル認証のトークン取得・aws-jwt-verifyでの検証・Amplifyからの接続を確認する。正式な認可実装はStep6で行う。
- 初回の依存関係取得に必要なネットワークと、コンテナの起動手順を記録する。

成果物: 起動設定、ルート設定ファイル、モノレポ骨格、起動手順、認証接続の検証記録。

完了条件:

- 新規環境からコンテナを作成し、DBへ接続できる。
- 認証接続の成立を確認できる。成立しない場合は対応方式を決め、後続Stepへの影響を記録する。
- `.env`なしで起動でき、ホストへの依存関係インストールを必要としない。

**手動作業:** ユーザーがGitHubリポジトリを作成し、Step0〜1の成果物を初回pushする。既存成果物を利用する場合はここで確認する。

### Step2: CI・commit hook・共通基盤

実施内容:

- GitHub Actionsで依存関係インストール、lint、typecheck、test、buildの実行基盤を作る。
- Huskyのpre-commitを整える。CIを最終的な品質確認とし、hookだけに依存しない。
- `packages/config`で環境変数の検証、`packages/logger`でログと秘密情報の除外を整える。
- フロントのVitest/Playwright、バックのNode Test Runner/Chaiを段階的に導入する方針を決める。
- テストがまだない対象はその状態を明記し、空のテスト実行を品質達成と扱わない。

成果物: 基盤CI、commit hook、設定検証、logger、共通実行コマンド。

完了条件: コンテナ内とCIで同じ品質チェックが動き、意図的な型・lintエラーを検出できる。

### Step3: Database Contract

実施内容:

- 商品、注文、注文明細をSQLで定義し、購入者識別、価格スナップショット、状態、日時を含める。
- 在庫を商品行に持つか別テーブルに持つかを決める。同じ在庫数を複数箇所に保持しない。
- 一意制約、外部キー、価格・数量・在庫のCHECK制約、検索用インデックスを定義する。
- migrationの適用順序と履歴管理、seed、テストDB初期化を整える。
- `schemas/tables/views/functions/policies`等は必要に応じて追加し、migrationsとの関係を説明する。
- スキーマ変更はSQL migrationsを経由し、最新スキーマ一覧は適用結果から生成する。
- 実PostgreSQLでCHECK制約・一意制約などを直接検証し、Prismaでは表現できない制約も対象にする。

成果物: SQL migration、seed、ER図・DB設計、適用・初期化スクリプト。

完了条件:

- 空のDBからスキーマを再現し、重複適用を防げる。
- 重複コード・負数在庫・不正数量などをDB制約で拒否できる。
- APIの入力検証を経由しないDBへの書き込みで、対象制約が不正値を拒否することを確認できる。
- 最新スキーマ一覧をSQL migrationsから再生成でき、手編集による二重管理がない。
- DB統合テストをCIで実行できる。

### Step4: Prisma生成フロー

実施内容:

- `packages/prisma`で`prisma db pull → prisma generate`を整備する。
- APIから利用するClientの公開方法と生成先を定める。
- 生成に必要な設定と、生成結果の再現性を整理する。
- 一時DBへのmigration適用からPrisma生成までをCIへ追加する。
- 生成元は空の一時DBへGit管理されたSQL migrationsを適用した結果とし、開発DBの状態に依存させない。

成果物: 生成スクリプト、生成Schema/Client、利用手順。

完了条件: 空のDBへのSQL適用からSchema/Clientを再現し、テストDBで読み書きできる。開発DBへの直接変更とSchemaの手編集が不要である。

### Step5: API Contract・OpenAPI・Client

実施内容:

- 商品登録・一覧、商品検索・在庫表示、注文作成・参照・確定・キャンセルの契約を定義する。
- 注文参照は画面表示に必要な補助APIとして扱う。
- URL、HTTPメソッド、入力、出力、ステータスコード、認証、共通エラー形式を定義する。
- `packages/api-contracts`にRoute DefinitionとZodスキーマを置き、public/privateのOpenAPIを生成する。
- `packages/api-client`へ型付きClientを生成し、Axiosとの連携を整える。
- APIアプリが契約を利用してルートを登録する方式を整える。
- 契約スキーマをOpenAPIへ生成可能な形式に限定し、実データに依存する業務条件はサービス層の検証へ分ける。
- Request検証と、APIアプリ側の送信前Response検証に同じ契約を利用する。共通Response検証の実装はStep7で行う。
- 再生成と契約チェックをCIへ追加する。
- 既定ブランチとのOpenAPI比較で破壊的変更を検出し、影響・理由・移行方法のPR記載ルールを整える。検出ツールはこのStepで選定する。
- フロント向け入力スキーマの直接公開と、OpenAPIからのスキーマ生成を比較し、Step9の検証方式へ引き継ぐ。

生成・利用の流れ:

```text
packages/api-contracts ──→ schemas/openapi ──→ packages/api-client
          │
          └──→ apps/public-api / apps/private-api
                    契約を利用して業務ハンドラーを登録
```

成果物: 全対象APIの契約、OpenAPI、Client、生成・検証コマンド。

完了条件: 全APIの正常系・異常系が仕様化され、契約から生成でき、入力・応答の不一致を検出できる。破壊的変更の比較チェックがCIで動作する。

### Step6: 認証・認可

実施内容:

- Step1の検証を基に、cognito-localのUser Pool/Clientと管理者・購入者のテスト利用者を初期化する。
- `packages/auth`でJWTの署名、有効期限、issuer、用途、対象Clientなど必要な条件を検証する。
- 管理者判定と、注文所有者によるアクセス制限の仕組みを作る。
- Amplify設定とログイン・ログアウトの接続方法を整える。
- ローカルと配備先での認証設定の差分を記録する。

成果物: 認証・認可ライブラリ、初期化スクリプト、フロント設定、認証テスト。

完了条件: 正常なトークンを受け入れ、無効・期限切れを拒否し、管理者以外の管理操作を拒否できる。注文所有者の最終検証はStep11で実注文に対して行う。

### Step7: バックエンドアプリ

実施内容:

- public/private APIをHonoで起動し、契約、Prisma、認証・認可を接続する。
- エラー処理、CORS、ログ、ヘルスチェック、終了時の接続処理を整える。
- 業務処理とDBアクセスの責務、トランザクション境界の置き場所を定める。
- DBモデルとAPI DTOを分離し、公開項目と金額・日時などを明示的に変換する。
- 契約スキーマによる送信前Response検証を共通処理として実装し、正常・業務エラー・認証エラーなど対象APIの応答へ適用する。
- 検証失敗時は不正な応答を送信せず、内部情報を含まない契約済みサーバーエラーを返し、秘匿化したログへ記録する。エラー処理の再帰を防ぐ。
- `packages/test-utils`に必要なテストDB・APIテストの共通処理を置く。
- 未実装の業務APIは正常動作しているように返さず、完成状態を明示する。

成果物: 起動可能な2 API、共通ミドルウェア、DTO変換方針、共通Response検証、APIテスト基盤。

完了条件:

- 両APIの起動、DB接続、認証エラー、共通エラー形式を自動検証できる。
- 不正なレスポンスを検出し、その本文と内部情報を送信せず、契約に沿ったサーバーエラーを返してログへ記録できる。
- DTO変換と共通Response検証の適用を確認でき、エラー応答で検証処理が再帰しない。

### Step8: Screen Contract

実施内容:

- 管理用の商品登録・一覧、購入者向け検索・在庫表示・注文操作の画面契約を定義する。
- 画面ID、ルート、権限、入力、API、遷移、読み込み中・空・成功・失敗の状態を記述する。
- 受け入れシナリオIDとE2Eシナリオを対応付ける。
- 画面Docs生成、ルート照合、E2Eの対応漏れ検出を実装する。
- ルートの存在確認と業務動作のE2Eを区別し、後者を省略しない。

成果物: Screen Contract、生成Docs、ルート・E2E対応の検証コマンド。

完了条件: 定義した画面と仕様を照合でき、画面ID・ルート・E2E対応の不一致をCIで検出できる。画面実装後は実ルートに対して検証する。

### Step9: フロントエンド基盤

実施内容:

- Vue、Element Plus、TypeScript、Zod、Axios、TanStack Query、Amplifyで両フロントを構築する。
- Screen Contractに沿ったルート、ログイン、アクセス制御、共通レイアウトを実装する。
- 生成Client、クエリ・更新処理、APIエラー表示を接続する。
- フォーム検証を行う範囲、UI入力からAPI入力への変換、スキーマの共有・生成方式を決定する。APIルールを手書きで複製せず、ブラウザ用コードへDB・認証実装・サーバー起動処理を混ぜない。
- `packages/ui`には必要な共通部品を追加する。
- VitestとPlaywrightの実行基盤をCIへ追加する。

成果物: 起動可能な2フロント、共通UI、認証画面、テスト基盤。

完了条件: ログイン・ログアウト、ルート遷移、権限別の表示、API接続が動作し、実ルートと画面契約を照合できる。

### Step10: 商品管理・検索・在庫表示

実施内容:

- private側の商品登録・一覧をAPIから画面まで実装する。
- public側の商品コード・商品名検索、在庫表示を実装する。
- 入力制約、重複コード、空の検索結果、API失敗時の表示を実装する。
- API・DBテスト、必要なUIテスト、登録→検索のPlaywrightテストを追加する。
- Step0の受け入れシナリオを基に業務テストを作り、契約から生成する形式検証と分けて維持する。

成果物: 商品機能一式と関連テスト。

完了条件: 管理者が登録した商品を購入者向け画面で検索でき、保存された在庫数が表示される。正常系・異常系・権限制限がCIを通過する。

### Step11: 注文・在庫引当・キャンセル

**重要:** 在庫不足チェックと排他制御は注文確定と同じStepで実装する。

実施内容:

- 注文作成・参照・確定・キャンセルのAPIと画面を実装する。
- 注文所有者を検証し、他の利用者による参照・操作を拒否する。
- 注文状態と在庫更新を同一トランザクションで扱う。
- 悲観ロックを標準案とし、注文行と在庫を保持する行をロックしてから状態・在庫を確認する。
- 複数商品は一定の順序でロックしてデッドロックの発生を抑える。発生時の失敗・再試行方針も定める。
- 在庫不足時は全商品の引当と注文状態の変更をロールバックする。
- draftのキャンセルで在庫を戻さず、confirmedのキャンセルでは一度だけ戻す。
- 同一操作の再送でも二重引当・二重復元をしない。注文作成の再送はStep0で決めた方式を実装する。
- 注文金額はサーバー側で契約・保存価格に基づいて計算する。
- 在庫・状態・所有者などの業務条件をサービス層で検証し、受け入れ要件に基づくテストで結果を確認する。
- 操作後の注文・在庫表示を更新し、二重送信時のUIとAPI双方の挙動を整える。

成果物: 注文機能、トランザクションとロック処理、正常系・異常系・基本競合テスト。

完了条件:

- 作成→確定→キャンセルの在庫増減が仕様どおりである。
- 不足時の全体ロールバックと、再送時の二重更新防止を確認できる。
- 他人の注文を操作できず、基本的な並行確定でも在庫が負数にならない。

### Step12: 排他制御・契約・E2Eの重点検証

実施内容:

- 実PostgreSQLの別接続から並行処理を開始して検証する。モックや単なる逐次実行で代替しない。
- 在庫1の商品に2注文を同時確定し、成功1件・失敗1件・在庫0を確認する。成功者は固定しない。
- 同一注文の二重確定、二重キャンセル、確定とキャンセルの競合を検証する。
- 複数商品の一部不足、途中失敗、ロールバック後のロック解放を検証する。
- 楽観ロックを比較用の実験・テストとして実装し、競合検出、再試行、悲観ロックとの差を記録する。標準実装を無条件に二方式へ分岐させない。
- 全APIの契約検証、生成物の再現性、Screen Contractと実ルート・E2Eの整合性を確認する。
- 業務要件から定義した受け入れ・競合テストの対応を確認し、契約との整合性チェックだけで完了扱いにしない。
- 空のDBからSQL適用・Prisma生成を再現し、DB制約とAPIアプリ側のResponse検証が有効であることを確認する。
- 商品登録から注文キャンセルまでの主要経路をPlaywrightで検証する。

成果物: 並行実行テスト、契約・生成チェック、主要E2E、排他制御の比較記録。

完了条件: 在庫非負、注文状態と引当の整合、復元が一度だけ行われることを競合下でも確認でき、全チェックがCIを通過する。

### Step13: ドキュメント最終整理

実施内容:

- 各Stepで更新した文書をVitePressで整理する。VitePressはREADMEへの追加ツールとして記録する。
- API・画面の文書は契約から生成し、手書きの重複仕様を作らない。
- DB・API・画面の生成フロー、認証、排他制御、起動・テスト・課題解決の手順をまとめる。
- READMEから必要な手順・契約・学習記録へ辿れるようにする。
- 文書のビルドと生成文書の整合性をCIで検証する。

成果物: VitePressドキュメント、更新README、設計判断・学習記録。

完了条件: 新規参加者が文書だけで環境起動・生成・テストを再現でき、文書ビルドが成功する。

### Step14: コンテナ配備・CD・運用確認

実施内容:

- 配備先、レジストリ、公開経路、DB、Cognito、Secret管理、Terraformの管理範囲を決める。
- フロントのビルド成果物配信とAPI実行の方式を定め、配備用イメージを作る。
- 開発設定と配備設定を整理し、cognito-localを検証・本番用認証へ置き換える。
- GitHub Actionsにイメージビルド・配布・検証環境への配備を組み込む。
- DB migrationとアプリ配備の順序、ヘルスチェック、アプリ復旧、DB変更の復旧方針を定義する。
- DB・API・フロントの新旧版が共存する期間を想定し、互換性を保つ変更と配備順序、破壊的変更時の移行方法を定める。
- 検証環境で認証、商品操作、注文操作、在庫整合性を確認する。
- 配備・ログ確認・障害対応の手順を文書化する。

成果物: 配備用Dockerfile、CD、必要なTerraform定義、運用手順、検証記録。

完了条件: 検証環境へ再現可能な配備ができ、主要シナリオ、旧版との互換性、配備順序と復旧手順を確認できる。配備先が未決定ならこのStepは未完了とする。本番公開の範囲は配備先決定時に確定する。
